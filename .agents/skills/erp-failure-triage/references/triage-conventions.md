# AutoERP 失败分析约定

## 1. 证据来源与解释边界

AutoERP 的常见证据及其实现来源如下：

| 证据 | 可确认内容 | 实现来源 |
|---|---|---|
| API YAML 执行信息 | YAML 路径、用例名、场景步骤、请求 URL、变量来源 | `api/framework/runner.py` |
| API 断言详情 | 断言类型、期望值、实际值、多个断言失败汇总 | `api/framework/assertions.py` |
| API 请求与响应摘要 | 请求方法、脱敏后的参数/头、响应状态与正文摘要 | `api/framework/http_client.py` |
| JUnit | 测试节点、失败消息、测试时长 | `run.py` 中 `--junitxml` 配置 |
| Allure | 分运行目录的结果、附件与环境信息 | `run.py` 中运行 ID 和 `--alluredir` 配置 |
| UI/E2E 截图、视频、Trace | 页面状态与操作轨迹；必须先脱敏并确认属于同一次执行 | `run.py`、`ui/conftest.py` |
| E2E 跨层检查 | 运行 ID、单据号、数据库对象 ID、库存前后值 | `e2e/conftest.py`、`e2e/test_purchase_sales_e2e.py` |

原始 Allure、Trace、截图、请求头和认证状态可能含敏感信息。分析输入应优先使用经人工检查的最小化脱敏摘要，不得把 `.runtime/auth/`、Cookie、Token、密码或数据库连接信息作为材料。

## 2. 同一次执行的关联规则

每份证据至少记录：证据 ID、来源类型、脱敏路径、测试节点或用例名、测试层、运行 ID、时间、环境标签、业务对象标识以及关联状态。缺失项写 `未提供`。

只有同时满足下列关键条件时，才可把不同来源作为同一次执行的联合证据：

1. 运行 ID 或报告结果目录一致；
2. 测试节点、YAML 用例名或场景步骤一致；
3. 环境标签一致；
4. 涉及业务数据时，单据号、对象 ID、商品和仓库等关键对象能够对应；
5. 时间顺序合理，且附件存在直接归属关系或由同一测试节点产生。

任一关键条件冲突时不得合并。关键字段未提供时标记 `无法确认关联`，分别陈述事实。重试产生的每次 attempt 独立编号；后续成功不能抹去先前失败，也不能证明两次使用相同业务数据。数据库查询若缺少同一对象 ID、运行标识或合理时间窗口，只能作为背景，不能作为直接因果证据。

## 3. 事实、推断和未知

- **事实**：材料中直接可见，例如“断言期望 code 不等于 200，实际 code 为 200”。
- **推断**：由事实导出的解释，例如“测试预期可能与当前接口行为不一致”。必须列出证据和反证。
- **未知**：材料没有给出，例如正式产品规则、真实提交数量、并发操作、数据库事务顺序。

测试断言只能证明测试期望；接口返回只能证明观察到的行为。二者冲突不自动等于产品缺陷。没有 PRD、接口契约、经授权的验收结论或其他独立规则证据时，产品正确性保持待确认。

## 4. 分类与置信度

主分类限于：

1. 产品行为或接口契约问题
2. 自动化脚本与断言问题
3. UI 定位、元素状态和页面时序问题
4. 环境、代理或配置问题
5. 测试数据、状态隔离或清理问题
6. 证据不足，暂无法分类

置信度使用定性口径：

- `高`：直接证据形成闭环，且没有关键反证；仍需人工确认才能成为评分基准。
- `中`：有直接或多项间接支持，但存在一个关键缺口。
- `低`：仅能解释症状，缺少用于排除其他候选的证据。

候选根因最多三个，不能用多个近义说法凑数。

## 5. 验证与修复边界

只读核查可以包括：核对同一份脱敏报告、比较断言与实际、检查现有源码的控制流、核对证据关联字段、检查已提供的脱敏数据库查询结果。

以下操作必须单独列为 `需授权操作`：真实测试重跑、接口请求、UI 操作、数据库查询或写入、数据清理、配置变更、代码修改和依赖安装。报告应写明目的、前置条件、影响范围和风险，不得在分析阶段自动执行。

## 6. 反馈闭环

人工评审应逐项记录：无依据根因、错误故障分类、错误证据引用、跨运行证据混用、缺少必要事实、过度确定的结论和不安全的排查建议。收到反馈后仅修订对应条目，并保留“原候选—反馈—修订结果”的简要轨迹；人工另行决定是否确认根因。
